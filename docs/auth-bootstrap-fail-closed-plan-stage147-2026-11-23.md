## یافته‌های قطعی

### A. بازیابی نشست در AuthProvider خطاپذیر نیست
در `AuthProvider` تابع `sync`:
1. نتیجه `sb.auth.getUser()` را بدون بررسی `error` مصرف می‌کند.
2. `resolveBackendUser` را بدون try/catch اجرا می‌کند.
3. `setReady(true)` فقط در انتهای مسیر موفق اجرا می‌شود.
4. تابع هم در راه‌اندازی اولیه و هم از listener رویدادهای `SIGNED_IN`، `SIGNED_OUT` و `USER_UPDATED` فراخوانی می‌شود.
5. پرچم `cancelled` فقط cleanup کامپوننت را پوشش می‌دهد؛ چند اجرای هم‌زمان `sync` را نسبت به یکدیگر مرتب نمی‌کند.

بنابراین رد شدن Promise در بازیابی اولیه می‌تواند وضعیت `ready=false` را باقی بگذارد و اجرای هم‌زمان قدیمی می‌تواند پس از رویداد جدیدتر، وضعیت کاربر را بازنویسی کند.

### B. حل هویت، خطای دیتابیس را به نقش دانش‌آموز تبدیل می‌کند
در `resolveBackendUser`:
- خطای پرس‌وجوی `profiles` بررسی نمی‌شود.
- خطای پرس‌وجوی `profile_contacts` بررسی نمی‌شود.
- نبودن پروفایل و هر مقدار role ناشناخته به `student` تبدیل می‌شود.
- `active` بدون خواندن وضعیت فعال‌بودن حساب، همیشه `true` است.
- `authUser.id` مبنای شناسه است که درست است؛ نقش از metadata احراز هویت خوانده نمی‌شود که کنترل مثبتی است.

خطای دسترسی/شبکه نباید به هویت معتبر با سطح دسترسی پیش‌فرض تبدیل شود. نبودن ردیف پروفایل نیز باید خطای حل هویت تلقی شود، نه ایجاد ضمنی یک دانش‌آموز.

### C. انتخاب ستون نامعتبر هنوز روی main است
کد فعلی `profiles.select("id,full_name,name,role,created_at")` را اجرا می‌کند، درحالی‌که بررسی قبلی schema وجود ستون `name` را تأیید نکرده است. اصلاح این انتخاب در PR #7 پیشنهاد شده اما هنوز ادغام نشده است. تغییر این بخش باید با schema واقعی و PR #7 هماهنگ شود.

### D. مدل کاربر وضعیت فعال را اجباری می‌داند
`User.active` در `src/lib/domain/types.ts` اجباری است، ولی resolver فعلی آن را به‌صورت ثابت true می‌سازد. در بررسی فعلی هیچ ستون فعال/غیرفعال در query resolver خوانده نمی‌شود. پیش از افزودن نام ستون یا رفتار جدید، باید schema واقعی و قرارداد مدیریت حساب بررسی شود؛ از حدس زدن نام ستون یا تغییر schema خودداری شود.

## طرح اصلاح پیشنهادی (بدون تغییر DB)

### 1. Resolver باید fail-closed باشد
- نوع بازگشتی را به نتیجه صریح تبدیل کنید؛ برای مثال `Promise<User>` با پرتاب خطای دامنه‌ای مشخص برای شکست حل هویت، یا یک discriminated union که همه callerها را مجبور به بررسی کند.
- نتیجه `profiles` را همراه با `error` بررسی کنید؛ در خطای query یا نبودن ردیف، کاربر معتبر نسازید.
- فقط ستون‌های تأییدشده را انتخاب کنید: `id,full_name,role,created_at` (پس از تطبیق با schema و اصلاح PR #7).
- role را فقط در مجموعه دقیق `student | teacher | admin` بپذیرید. مقدار null یا ناشناخته خطاست؛ آن را به student تبدیل نکنید.
- خطای query مربوط به `profile_contacts` را نیز بررسی کنید. نبودن ردیف تماس می‌تواند اختیاری باشد؛ خطای query اختیاری نیست.
- نقش و وضعیت حساب را از `user_metadata` یا ورودی کلاینت استخراج نکنید.
- تا زمانی که فیلد فعال‌بودن حساب در schema و قرارداد محصول مشخص نشده، ادعای تشخیص حساب غیرفعال نکنید. اگر فیلد موجود و معتبر است، آن را صریحاً بخوانید و حساب غیرفعال را رد کنید؛ در غیر این صورت این قابلیت نیازمند تصمیم جداگانه است.

### 2. Auth bootstrap باید همیشه settle شود
- برای درخواست اولیه، خطای `getUser` را بررسی و به وضعیت خطای قابل نمایش تبدیل کنید.
- در `finally`، اگر effect هنوز فعال و درخواست جاری است، loading را پایان دهید.
- هنگام خطای شبکه/پروفایل، `userId` را null نگه دارید؛ از ورود نمایشی یا ساختن نقش دانش‌آموز fallback نکنید.
- به‌جای یک وضعیت مبهم signed-out، یک وضعیت خطای قابل بازیابی یا `authError` در context اضافه کنید تا رابط کاربری تفاوت «خروج واقعی» و «ناتوانی در تأیید نشست» را نشان دهد.
- برای هر اجرای sync یک شناسه ترتیبی/generation نگه دارید؛ فقط جدیدترین اجرا اجازه تغییر `userId` و وضعیت را داشته باشد. cleanup نیز همه اجراها را بی‌اعتبار کند.
- listener رویداد Auth باید سریع برگردد؛ کار async را خارج از callback زمان‌بندی کنید و از generation guard استفاده کنید تا نتیجه رویداد قدیمی پس از SIGNED_OUT یا ورود جدید اعمال نشود.
- برای SIGNED_OUT، وضعیت خروج باید بلافاصله اعمال شود و اجرای قدیمی نتواند دوباره کاربر را وارد کند.
- رویدادهای تکراری باید idempotent باشند؛ از ساختن چند درخواست موازی غیرضروری جلوگیری شود.

### 3. ورود مستقیم نیز باید خطا را امن نمایش دهد
`signIn` هم resolver را فراخوانی می‌کند. خطای حل هویت باید به خطای قابل نمایش و عمومی تبدیل شود، بدون نمایش جزئیات دیتابیس یا اطلاعات حساس. نشست احراز هویت‌شده با پروفایل نامعتبر نباید به context برنامه وارد شود. سیاست signOut/revoke برای چنین وضعیتی باید جداگانه و با توجه به رفتار Auth انتخاب شود؛ صرفاً خطای پروفایل را معادل موفقیت ورود ندانید.

## ماتریس آزمون الزامی

| سناریو | انتظار |
|---|---|
| getUser با کاربر معتبر و پروفایل student | ورود موفق با student |
| getUser با کاربر معتبر و پروفایل teacher/admin | نقش دقیق پروفایل؛ نه metadata |
| getUser با خطای شبکه | loading پایان یابد؛ کاربر null؛ وضعیت خطای قابل بازیابی |
| getUser بدون نشست و بدون خطا | signed-out واقعی |
| query پروفایل با خطا | حل هویت شکست بخورد؛ بدون fallback student |
| query پروفایل با ردیف صفر | حل هویت شکست بخورد؛ کاربر خودکار ساخته نشود |
| role برابر null یا مقدار ناشناخته | رد هویت؛ بدون تبدیل به student |
| query تماس با خطا | حل هویت شکست بخورد |
| query تماس با ردیف صفر و بدون خطا | ورود مجاز؛ phone خالی |
| پروفایل با full_name خالی | فقط fallback نام نمایشی غیرحساس؛ role همچنان باید معتبر باشد |
| رویداد SIGNED_OUT درحالی‌که resolve قبلی معلق است | نتیجه قدیمی نتواند userId را برگرداند |
| دو رویداد SIGNED_IN پشت سر هم با تأخیر معکوس پاسخ‌ها | فقط نتیجه آخرین رویداد اعمال شود |
| unmount شدن AuthProvider در زمان query | هیچ state update پس از cleanup |
| خطای resolver در ورود دستی | خطای عمومی؛ هیچ userId معتبر تنظیم نشود |
| metadata دارای role=admin ولی profile.role=student | student؛ metadata نادیده گرفته شود |
| profile.role=admin ولی کاربر مجاز نیست | نقش فقط پس از RLS/سیاست سرور معتبر؛ UI به‌تنهایی مجوز محسوب نشود |

## روش اجرای تست و معیار پذیرش
1. برای resolver، SupabaseClient mock شود و پاسخ‌های `data/error` هر دو query کنترل‌پذیر باشند.
2. برای AuthProvider، `getUser` و `onAuthStateChange` mock شوند؛ deferred Promise برای آزمون race و unmount استفاده شود.
3. تست‌ها باید اثبات کنند که در هیچ خطای profile/contact یا role ناشناخته، `upsertVerifiedUser` اجرا نمی‌شود.
4. تست باید ثابت کند هر مسیر bootstrap در نهایت از loading خارج می‌شود و stale result نمی‌تواند وضعیت جدیدتر را بازنویسی کند.
5. پس از پیاده‌سازی، اجرای `bun run test` و `bun run build` در CI لازم است.
6. آزمون‌های بالا جایگزین آزمون نقش‌های واقعی anon/student/teacher/admin روی staging نیستند؛ تا وقتی محیط staging و حساب‌های آزمایشی اختصاصی وجود ندارند، رفتار واقعی RLS/API تأییدشده تلقی نمی‌شود.
